# WB API для управленческого учета

_WB API может быть удобным инструментом, так как позволяет загружать работать с данными напрямую минуя портал WB. На основании данных выгрузок можно быстро строить аналитики и PL. Однако есть ряд вопросов которые требуются уточнить что бы отчетность шла в рамках портала WB и бухгалтерии._


## 1. Исходные данные
Нас интересует детализированный отчет о реализации, полученный через WB API.
Источник: https://statistics-api.wildberries.ru/api/v5/supplier/reportDetailByPeriod

__Ограничения WB:__

-	Минимальная дата — 29 января 2024 года
-	Периодичность — день / неделя
-	Интервал между запросами — 1 минута
-	Ограничение — 100 000 строк на запрос

В итоге, чтобы скачать все данные, ушло более 10 часов. Я грузила по дням что бы не зависить от недельных отчетов.

Все raw-данные сохранены в отдельную таблицу PostgreSQL.

__Объем данных__
- Период: 29 января 2024 — 2 февраля 2026
- Всего загружено: 11 833 588 строк.

## 2. Состав данных

Каждый JSON документ содержит от 85 до 90 полей. Поля меняются в зависимости от времени и типа операции. Сделать итоговорую таблицу из выгрузок можно, но нужно постоянно мониторить изменения WB что бы обрабатывать новые поля и изменения методики расчетов. 

Сырые данные отчета представляет собой ненормализированную выгрузку — фактически большое _неструктурированное месиво из данных_.

После загрузки база данных была нормализизирована. Официальная документация WB и документация к WB API противоречива. Оферта так же не дает ответы как использовать полученные данные. Сложно сопоставить поля выгрузки с описанием полей в официальной документации, а так же в официальной документации отсутствуют детали, которые могли помочь корректно разносить данные.

В таблице ниже - mapping полей api и документации к порталу а также вопросы и комментарии.

## 8 СОЗДАНИЕ ПРЕДСТАВЛЕНИЙ И ИТОГОВОЙ ТАБЛИЦЫ ДЛЯ УЧЕТА

> ❗️❗️ ВАЖНО 
>> В том виде аггрегированный отчет, который мне прислали в файле `fin_report_1.xlsx` может давать существенные погрешности в учете по следующим причинам:

1. Дата 
 - стоит `date_from` я бы брала `sales_dt` если мы признаем выручку и услуги по факту продажи;
 - тип данных date вместо datetime. Если неправильно отрезали время (например другой часовой пояс) часть операций сместиться относительно отчетной даты. Нужно строгое правило или UTC или UTC + 3 (МСК).

2. Barcode 
- Излишняя агрегация по баркодам. Не имеет смысла для PL;
- Баркоды не уникальны сами по себе (см документацию WB), для нормальной агрегации нужен составной ключь артикль - цвет - размер - баркод. Иначе возможны аномалии и задвоения, особенно где nm_id NULL;
- nm_id вполне достаточно, что бы найти ставку НДС из карточки или по ТНВЭД.

3. Brand
- Излишняя агрегация по Брендам. Не имеет смысла для PL;
- В карточках товаров косяки, а следовательно и в агрегации будут. Наприме: bershka и Bershka + баркод к двум и более артиклям + два бренда к одному артиклю -> получаем ошибки. Без нормализации и стогих JOINов работать не будет. 
- Если нужна аналитика из факта по баркодам и брендам - m2m таблицы / представления и уникальные составные ключи и / или использовать `srid` для группировки. 

4. Операции по каждому флагу и типу имеют свою специфику и агрегировать их _«в лоб»_ плохая идея
- Знак имеет или не имеет значение в некоторых случаях - нужно вести учет по модулю;
- Специфика флага 0 и 1 разная. Нужно агрегировать с учетом флагов;
- Перед агрегацией нужно превести данные в _«длинную»_ форму (GL). Предварительно нормализовав данные, спавочники и ключи. Тем самым избавимся от анамалий. Пытаться агрегировать фактуру - не лучший вариант.
- Без двойной записи проверка результатов не возможна.

### СОЗДАНИЕ ДЛИННОЙ ФОРМЫ ИЗ ФАКТОВ - GL

Длинная форма представляет собой general ledder (GL) управленческого учета по описаному выше плану счетов и методики. Основные поля финального представления следующие:

- srid - сквозной трекер заказа (храним через ключ id - srid)
- rrd_id - номер строки (храним в через ключ id - rrd_id)
...

Агрегация правильная и доступна на всех уровнях. Можно подтяную сколько угодно релевантных связанных Субконто. По srid или rrd_id, можно подтянуть любую аналитику (баркоды через m2m, бренды через nm_id, даты, количество и прочее). Расчитать любые метрики (оборачиваемост / маржинальность / рейтинги и пр.).

- Дебитовое Сальдо по счету Расчеты с WB записываем в BS (Денежные средства и эквиваленты);

- Кредитовое Сальдо по родительским счетам 'Себестоимость' + субконто 'Прочие доходы' даст нам Cash cost и маржу текущего периода;
- Кредитовое Сальдо по родительским счетам 'Себестоимость' + 'Расходы' + 'Выручка' даст нам PL
- Сальдо по счету Расчеты по НДС записываем в BS в кредиторскую или дебиторскую задолженость
