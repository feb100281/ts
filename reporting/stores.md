# Учет входящего товара и себестоимости

_Существует проблема с определением бухгалтерской себестоимости, учетом остатков, списанию расходов. По данным анализа 45 счета:_

В настоящее время процесс организован следующим образом:

1. При поступлении партии товара (импорт или закупка в РФ) сначала запрашивается связка: артикул + размер + цвет + штрихкод. Обычно это мэппинг или отгрузочный файл. В последнее время данные запрашиваются у Карины, ранее их предоставляли Седа и Богдан.

2. На основании этой связки программист формирует новый УПД из товарной накладной. Каждому товару присваивается уникальный баркод — таким образом закупленный товар приводится к формату, в котором он продается на WB. В 1С товары загружаются в виде: наименование + баркод + размер.

3. Далее выгружается вся номенклатура из 1С (частями, из-за ограничения по количеству строк), проверяется на наличие дублей, сверяется с номенклатурой в новом УПД. Новые позиции выделяются и дополнительно загружаются в 1С. Для каждой партии создается отдельная папка.

4. После обновления номенклатуры выполняется загрузка УПД. При этом ранее возникала проблема: с октября 1С перестала сопоставлять товары по баркоду, и сопоставление стало происходить по названию и размеру. В результате при загрузке часто требуется вручную выбирать нужный товар по баркоду, так как совпадений по названию может быть много.

5. После оприходования товар сразу отгружается на WB.

6. Далее выполняется обработка продаж. Детализация продаж выгружается из личного кабинета в Excel. Файл приводится к унифицированному виду: наименование, размер и баркод выносятся в отдельные столбцы, также к наименованию подтягиваются размер и баркод для корректного сопоставления проданных товаров с закупленными.

7. После этого файл загружается в 1С. Ранее процесс был во многом автоматизирован за счет сопоставления по баркоду, однако после изменения алгоритма 1С сопоставление стало происходить по названию, что привело к необходимости ручной обработки.

8. В настоящий момент сопоставление по баркоду в 1С восстановлено, в связи с чем обработка продаж должна снова выполняться в почти автоматическом режиме.

Описанный выше процесс выглядит достаточно трудоемким и вероятнее всего не будет работать. Ниже мои комментарии по каждому пункту:

1. Что представляет собой мэппинг или отгрузочный файл.  Данные хранятся в разных файлах excel? Как формируется связка  артикул + размер + цвет + штрихкод? Если речь идет о тех файлах, которые присылала Карина, то я уже писала комментарии по поводу определения уникальных артикулов. Фактически обрезается часть артикля и добпаляется константа в конец, как следствие получаем неуникальные артикли и ошибки на начальном этапе. Причины для этого следующие:
    - Алгоритм мэппинга должен осуществляться поверх excel. Файл эклель может служить сырыми данными для импорта в базу данных, и то excel самый плохой вариант для этого. Лучше использовать текстовый csv вместо этого.
    - Должна быть четкая структура данных для хранения входящих документов:
        - Таблица с артиклями и уникальными ID;
        - Таблица с размерами и уникальными ID;
        - Таблица с цветами и уникальными ID;
        - Таблица связяей между ними с уникальностью по трем позициям, которая и генерирует ШК функцией с опредлененным алгоритмом (EAN-13 из id позиций например елси нужно детерминированый ШК или вообще брать UNIX TIME * rnd() если нужет рандом). Резать артикли и тем более добавлять константу - плохая идея. Вообще деалть что то руками для уникальности и тем более в excel лучше не стоит. 
    - Если нет размера, цвета, то ШК может генерироваться, но WB его не воспринимает. Структура данных карточки товара не требует уникальности ШК.
    - То есть уже на данном этапе нужен слой для работы с данными и данный слой ни в коем случае не может быть excel. 
    - Единственное назнаяение баркода и артикля быть уникальным. Других функций у них быть недолжно если хотим что бы система работала. Если все таки нужно что то зашифровать в них (не понимаю зачем), то нужна уникальная часть, а не константа.

То есть в УПД отсутсвует уникальность ключа (Артикула) и как следсвие пересортица.

Задачу по вводу вводу номенклатул нужно свести к очень простой логике:
- Выбор артикула продавца из карточек товара на WB (которые всегда уникальные) -> штрих код который привязан к конкретному артикулу в катрочке (если есть, но можно не ставить) ->  указание количества и цены без НДС. Все.
- УПД для загрузки в 1С должна формироваться по этим данным без каких либо расчетов и операций в excel. Excel не предназначен для такого и его можно / нужно полность исключить из процесса. 
- Наименавание, характеристи и прочие атрибуты (коды ТНВД, тэги, ставки НДС) тянутся из карточек товара напрямую в УПД по артиклю или составному ключу артикль + штрихкод.  
- Карточки всегда доступны по API WB. Если какой либо номенклатуры нет в карточках под нее должны быть зарезервированы уникальные артикли + штрихкода если приемлемо. 
- На коленке можно сделать базу SQLite / PSQL c 2-3 таблицами для этого. Всести ее гораздо проще чем 54+ файлов в excel. Импорт / Экспорт данных в 1С через xml, txt, json или тот же excel / csv одним запросов. Обновление данных карточек через WB API ежедневно 1 запросом. 
- Это не исключит все возможные ошибки в бух учете, но по крайней мере наведет порядок со справочниками и приходами, исключит человеческий фактор и абсолюно ненужную прослойку в виде excel.

## Сопастовление с WB

- 21789 артиклей сопроставились с карточками товара WB
- 590 артиклей из УПЛ не сопоставились с WB
- 6883 артиклей из карточек товаров не сопоставились с УПД

### Проблемы при сопоставлении

При сопоставлении с карточками товара:
- более 2.5 тыс артиклей из УПД сопоставляются с __двумя и более__ карточками товаров (лист `upd_product`)
- 1282 артикля WB из карточек товаров имеют соответсвия с __двумя и более__ артиклями УПД.
- 17158 номенклатур с УПД сопоставляются но пересортица присутсвует как минимум в 1688 единицах.

Следовательно мы можем только использовать 17158 - 1688 = __15,470 артиклей__ для сопоставления напрямую. Остальные артикли в УПД нужно менять руками для соответсвия карточкам товаров.

### Решение - временное

Я разделила номенклатуры WB и номенклатуры УПД по группам. 
Родительская группа в УПД - агрегирует расходы и количество. Затем получены средние показатели по c/c распредлеяем на номенлатуру WB. В дальнейшем можно применить FIFO

Достаточно грубо, в этом случае мы сможем списать на прожажи уже:

- 943,721 ед товара (меньше на 5.84% закупок)
- 1,018,805,013 расходов (меньше на 8.30% закупок)

Грузим продажи с февраля 2024 по декабрь 2025.

У нас 1 000 008 единиц товара было продано (без учета возвратов) на сумму 2,271,537 рублей.

Матчим с группами и пытаемся добавляем unit_costs. 
- Всего у нас за выбранный период торговалось - 22409 наименований.
- с/с нет у __4307__ позиций проданных товаров которые были проданы на сумму __206,309,271 рублей__. 
- То есть мы не смогли найти с/с на 20% проданного товара ~ 10% всего оборота за 2 года. __Это много__.

Тепер собираем inventories по группам.
